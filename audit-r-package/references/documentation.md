# Checklist: Documentation

Covers roxygen function docs, vignettes/articles, README, NEWS, and the pkgdown site. Read the roxygen blocks in `R/`, everything in `man/` (to confirm it's generated, not hand-written), `vignettes/`, `README*`, `NEWS.md`, and `_pkgdown.yml`.

## roxygen2 function documentation

- `man/*.Rd` are **roxygen-generated** (`% Generated by roxygen2` header). Hand-written `.Rd` that drifts from the code is a Warning.
- Every **exported** function has a roxygen block with, at minimum: a title, a description, `@param` for every argument, and `@returns`/`@return` describing the output. Missing `@returns` on an export is a CRAN blocker for new submissions - Warning/Critical depending on release intent.
- `@param` entries exist for all arguments and none that don't exist; documented args match the actual signature. Mismatches are an R CMD check WARNING.
- `@examples` present on exported functions, run without error, and finish fast. Code needing auth/network/long runtime uses `@examplesIf` (preferred) rather than `\dontrun{}`. Examples don't leave side effects (reset options, clean temp files).
- `@export` present on user-facing functions and absent on internal ones. Internal-but-documented helpers use `@keywords internal` + `@noRd` or are marked internal.
- Markdown roxygen is used (backticks, `[pkg::fun()]` auto-links) rather than raw Rd macros, and `@inheritParams`/`@rdname`/`@inheritSection` reduce duplication where sensible.
- Datasets are documented (in `R/data.R`) with `@format` and `@source`, and are never `@export`ed.
- A package-level doc exists (`"_PACKAGE"` sentinel in `R/{pkg}-package.R`) giving `?pkg` help.
- `RoxygenNote` in DESCRIPTION isn't wildly behind the installed roxygen2.

## Vignettes and articles

- If the package is non-trivial, at least one vignette exists and is problem/workflow-oriented (not just a list of functions).
- Vignettes live in `vignettes/`, have correct YAML (`VignetteIndexEntry` matching the title, `%\VignetteEngine{knitr::rmarkdown}`, UTF-8), and `VignetteBuilder`/knitr/rmarkdown are declared.
- Every package used in a vignette is a formal dependency (Imports or Suggests). Fragile/credentialed code uses `eval=` guards.
- Content that can't run on CRAN (undeclared deps, heavy graphics, auth) is an **article** (`usethis::use_article()`, `.Rbuildignore`d) rather than a shipped vignette.
- `inst/doc/` is treated as generated - flag hand-edited built output.

## README

- A README exists and answers: what problem does this solve, how do I install it, a minimal usage example.
- Prefer `README.Rmd` rendered to `README.md` when it contains executed code, so examples stay current. A `README.Rmd` whose `README.md` is stale (out of sync) is a Note.
- Installation instructions are copy-pasteable and correct (CRAN and/or `pak::pak("user/repo")`).
- Badges (CRAN, R-CMD-check, coverage, lifecycle) present and not broken/misleading.

## NEWS

- `NEWS.md` exists and is maintained: one `# pkg (version)` heading per release, newest on top, dev version at top during development, user-facing changes in bullets, issue/PR references (`#123`) where useful.
- Entries are written for users (what changed and why it matters), not raw commit messages. A package with releases but no NEWS is a Note.

## pkgdown website

- If a site is intended: `_pkgdown.yml` present, `docs/` git-ignored, URL recorded in DESCRIPTION and `_pkgdown.yml` (needed for cross-package auto-linking), and deployment via `usethis::use_pkgdown_github_pages()` / a `pkgdown.yaml` workflow.
- For a package with many functions, the reference index is grouped meaningfully rather than one long alphabetical list.
- Consider dev mode `auto` for established packages so `/dev/` docs don't confuse users of the released version.
- `Config/Needs/website` used for website-only dependencies instead of adding them to Suggests.
